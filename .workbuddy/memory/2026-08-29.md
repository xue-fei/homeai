## server 端新增背景音乐播放（music 文件夹 / 16k mono wav）

### 架构决策：下行音频抽出唯一出口 PcmStreamer

原来 TTS 自带发送线程。加音乐后如果各自开线程往同一个 WebSocket 推 PCM，
两路字节会交织 → ESP32 收到的是两段音频被随机切碎拼接 → 纯噪音。
所以把发送职责从 TTS 剥离，新建 `PcmStreamer.cs` 作为全链路唯一 PCM 出口。

抢占模型用 generation 令牌：
- `Acquire(producing, drained)` → 代号自增 + 清队列，返回新代号，调用方成唯一生产者
- `Push(frame, gen)` → 代号过期返回 false，生产者据此得知被抢占
- 语音 Acquire 即抢占音乐；语音结束触发 `OnIdle`，音乐自动接回

### 新增文件
- `PcmStreamer.cs` — 唯一 PCM 出口。Stopwatch 节拍 + 60ms/包 + 起播水位 20 帧 +
  队列满阻塞反压（绝不丢帧）
- `WavStreamReader.cs` — 流式 WAV 读取。**按块遍历**而非固定偏移（fmt/data 之间
  可能夹 LIST/fact 块）；严格校验 16k/mono/16bit，格式不对直接抛异常；
  支持 `Rewind` 用于被抢占后回退未播出的部分
- `MusicPlayer.cs` — 播放器。四态：Stopped/Playing/Paused/**Ducked**
- `MusicCommandParser.cs` — 规则匹配音乐语音指令（不走 LLM）

### 三个踩过的坑（重要）

1. **Ducked 必须区别于 Paused**。用户按暂停后，语音说完不该自己响起来；
   被语音压下去的，说完就该接回来。合成一个状态行为会很怪。
2. **音乐必须自限预读深度**（`MusicBufferFrames = 50` 即 1s，远小于出口 8s 上限）。
   音乐是取之不尽的流，放开推会瞬间灌满 8 秒，导致：State/CurrentName 超前真实音频
   8 秒（日志和状态回执全是假的）、被抢占时白丢 8 秒且 Rewind 可能已跨到下一首、
   短文件在读取阶段就"播完"并连续切歌。TTS 不需要此限制——语音有限长，攒满是好事。
3. **Ducked 需要看门狗轮询**。`OnIdle` 只在正常播完时触发；语音被 `Interrupt` 强行
   掐掉时出口直接失效、无 OnIdle，音乐会永远卡在 Ducked。PumpLoop 里加
   `TryResumeFromDuck()` 每 200ms 轮询 `streamer.IsIdle`。

### 改动的已有文件
- `Tts/TtsMatchaIcefall.cs` — 删掉自己的 SendLoop/sendQueue，改走 PcmStreamer；
  构造函数签名变为 `TtsMatchaIcefall(PcmStreamer)`；新增 `OnSpeechStarting` 让位钩子
- `Server.cs` — 组装 streamer/music；`HandleMusicCommand`；新增 code=3 音乐控制协议；
  `UpdateClient` 由 tts 改为 streamer；OnClose/心跳超时时 `music.Stop()`
- `Asr.cs` — 新增 `CommandInterceptor` 钩子，识别结果先过音乐指令，命中则不送 LLM
  （「下一首」绕一圈 1.5B 模型既慢又会变成聊天）
- `Program.cs` — 控制台调试指令 play/pause/resume/stop/next/prev/vol/loop/list/scan/state
- `server.csproj` — music/**/*.wav 随生成输出

### 验证
- WavStreamReader 单测：正常读取、Rewind、含 LIST 块解析、双声道/44.1k/8bit 拒绝
- 指令解析单测：17 条正例 + 4 条负例（「音乐是人类的语言」不得误判）
- 集成测试：抢占→Ducked→自动恢复、Paused 不自动恢复、切歌、停止后停发、播完自动续下一首
- 全部通过；`dotnet build -t:Compile` 0 错误 0 警告

### 使用
wav 放 `server/music/`（16000Hz 单声道 16bit）。语音说「播放音乐」/「下一首」/
「暂停」/「声音大一点」等；或客户端发 `{"code":3,"msg":"播放音乐"}`。
默认音量 0.6，列表循环开。

## server 端新增天气查询（心知天气 API）

### 文件
- `WeatherService.cs` — 心知天气 v3 API 客户端（实况 + 预报）
- `WeatherCommandParser.cs` — 规则匹配天气语音指令（不走 LLM）

### 架构
asr.CommandInterceptor 链：先天气 → 再音乐 → 再 LLM。
WeatherService 从环境变量 `SENIVERSE_KEY` 读 key，没 key 时天气功能不可用，
但其它功能照常。

### 指令
- 实况：「今天天气怎么样」「北京气温」「明天要带伞吗」
- 预报：「明天天气」「后天成都天气」「未来几天」
- 时态词：明天/后天/大后天 → forecast，其余 → 实况
- 城市提取：已知城市列表 +「XX天气」模式匹配；「今天/明天/未来」等时间词黑名单
- 排除：「天气预报员说...」这种不算查询

### 测试
16 条正例 + 4 条负例全部通过。

### 配置
```bash
set SENIVERSE_KEY=your_key_here
dotnet run
```
心知天气免费版：天气现象、代码、气温 3 项数据，1 次/秒。

## 修复：MusicPlayer 预读深度限制

第一版 MusicPlayer 靠 PcmStreamer 的 Push 反压（8s 上限），但音乐是无穷流，
会瞬间灌满队列 → State/CurrentName 超前真实音频 8 秒、被抢占时白丢 8 秒、
短文件在读取阶段就"播完"并连续切歌。加 1s 预读上限（MusicBufferFrames=50）后
集成测试全部通过。

## 修复：Ducked 状态需要看门狗

OnIdle 只在语音正常播完时触发。用户按键打断 TTS 走 Interrupt → 出口直接失效
无 OnIdle → 音乐永远卡在 Ducked。PumpLoop 里加 TryResumeFromDuck() 每 200ms 轮询
streamer.IsIdle。
