# 2026-09-12

## 修复：TTS 播放卡顿/欠载暴涨（根因 = 服务端"攒帧"卡死供给）

### 症状（ESP32 串口日志）
- 缓冲帧长期 = 0/64，欠载从 2064 一路涨到 3129（每 5 秒涨 40+）
- 只在几十秒后才偶尔出现「缓冲帧=1」，说明服务端几乎没在发数据
- 「讲一个长一点的玄幻小故事」这类长文本时尤其严重

### 根因
PcmStreamer.SendLoop 的「攒帧」逻辑与 TTS 的「突发供给」不匹配：

1. **攒够 FramesPerPacket(6) 帧才发**：TTS 推帧是突发式的（一段 PCM 一次灌几十帧，
   然后又空几秒）。短句/句首只有 1~5 帧时永远凑不满 6 帧 → 一个字节都不发 →
   ESP32 的 1.28s 缓冲被抽干 → 欠载暴涨。
2. **起播水位 StartWatermarkFrames=24(480ms) 太高**：首句冷启动（LLM 首 token +
   Matcha 首次推理）期间队列攒得慢，凑不满 24 帧就一直卡在"预缓冲"不发。

### 修复（PcmStreamer.cs）
1. `StartWatermarkFrames` 24 → **1**。防爆音预缓冲职责交给 ESP32 侧（它冷启动攒
   200ms 才开声），服务端不再攒帧——攒帧只会加大首字延迟，且在突发供给下永远
   凑不满水位。
2. 发送逻辑从「攒够 6 帧才发」改为「**有数据就发**」：`maxFrames = Math.Min(6,
   queue.Count)`，队列有 1 帧发 1 帧、有 50 帧每轮发 6 帧，只要队列非空就持续发。
   删掉了 `if (due - framesDue < FramesPerPacket) sleep` 这个卡顿判据。
3. 保留节拍上限 `due - framesDue > MaxQueueFrames(400)` 防发送过快冲爆 ESP32 缓冲
   （但 TTS 突发场景基本触发不到，音乐流才有意义）。
4. 加了 5 秒周期诊断日志 `[PCM] 队列=N 已发=M 生产中=b started=b`，用于区分
   「供给不足」还是「发送卡住」。

### 关键认知
- 服务端丢帧/攒帧都会导致 ESP32 欠载；供给速率必须 ≥ 播放速率(50帧/秒)。
- Matcha 推理 20~40 倍实时，供给不是瓶颈；瓶颈只在"句间停顿 + 攒帧不发货"。
- 句间停顿靠 `PatienceMs(2000)` + TTS 的 `KeepAliveMs(2500)` 兜底，防止误收尾。

### 待办
重启服务端后看 `[PCM]` 诊断日志确认队列水位正常（应持续非 0 或快速清空），
以及 ESP32 侧缓冲帧稳定在 20+、欠载不再持续增长。

## 修复（第二轮）：服务端发太快冲爆 ESP32 缓冲丢帧

### 症状（第二轮日志，方向反了）
- 缓冲帧 64/64（满），丢帧 2013 → 4146 → 4543 暴涨，欠载=0
- 最后一帧 缓冲帧=0、欠载=1（发完一波就停，缓冲抽干）

### 根因
上一轮把「有数据就发」做过头了：`SendAheadLimitFrames` 用的是 `MaxQueueFrames=400`
（8 秒），等于「队列有数据就疯狂发」。TTS 推理完瞬间把几十秒音频一口气全灌给
ESP32，其 64 帧(1.28s) 抖动缓冲瞬间灌满 → 之后每来一帧丢一帧 → dropFrames 暴涨。
丢掉的是已合成好的语音，听感跳字漏词。

### 正确认知（发送限速的核心）
服务端发送速率必须**严格贴合 50 帧/秒实时播放速率**，不是「有数据就发」，而是
「按实时节拍发，超前量不超过一个安全上限」。

### 修复（PcmStreamer.cs）
- 新增 `SendAheadLimitFrames = 32`（640ms）：`due - framesDue > 32` 就 `Sleep(2)`
  等待实时时钟追上来，把发送超前量钳制在 32 帧以内。
- 32 帧的选择：> ESP32 冷启动预缓冲(10帧)+DMA(12帧) 保证不欠载；< ESP32 缓冲
  上限 64 帧留安全距离，稳态下绝不触发丢帧。
- 稳态下这个上限其实用不到——发送速率被实时时钟钳在 50 帧/秒，超前量只小幅
  波动。它只兜「线程卡住后突然恢复疯狂追帧」的异常场景。

### 完整链路水位（最终版）
- 服务端：起播水位 1 帧（有数据立刻发）+ 发送超前上限 32 帧（不冲爆）
- ESP32：抖动缓冲 64 帧(1.28s)，冷启动预缓冲 10 帧(200ms)，中途欠载 RESUME 3 帧
- 配合后：起播快（首字延迟小），稳态贴合实时（不欠载不冲爆），句间停顿靠
  PatienceMs + KeepAliveMs 兜底不断音

## 修复（第三轮）：限速判据方向写反，限速器从未生效

### 症状（第三轮日志）
- 丢帧=400 突然出现一次，缓冲帧始终 0/64，欠载=1，「音频跳过了很多」

### 根因（关键 bug，教训深刻）
第二轮的限速判据写反了：
```csharp
double due = sw.Elapsed.TotalMilliseconds * framesPerMs;   // 实时应发帧数（小）
if (due - framesDue > SendAheadLimitFrames) { ... }        // 恒假！
```
`framesDue` 是「已发帧数」（快速发送时很大），`due` 是「实时时钟对应帧数」
（很小），所以 `due - framesDue` 恒为负，`> 32` 永远不成立 → 限速器从头到尾
没生效 → 服务端仍一口气把 TTS 推理出的几十秒音频全灌给 ESP32 → 缓冲瞬间灌满
丢 400 帧。

正确判据是**发送超前量 = framesDue - due**（已发帧数超前实时多少帧）：
```csharp
if (framesDue - due > SendAheadLimitFrames) { Thread.Sleep(2); continue; }
```

### 教训
写「超前量」类限速时，务必先想清楚哪个变量是「已做」、哪个是「应做」，
超前 = 已做 - 应做，不是反过来的。`due - framesDue` 这种写法一眼看就反了：
实时时钟(due)永远追不上已发帧数(framesDue)，除非发送线程被阻塞。

### 最终发送循环语义（正确版）
- 起播：sw.Restart + framesDue=0，快速预填到超前 32 帧（640ms），ESP32 快速开声
- 稳态：framesDue 与 due 同步增长，发送速率被钳在 50 帧/秒实时
- 句间停顿（< PatienceMs 不收尾）：due 持续涨而 framesDue 停滞，差值为负，
  新数据来了会「补帧」快速追上，ESP32 缓冲空着(64帧容量)能接住，不丢帧

## 新增：LongCat 云端 LLM 后端

### 背景
新增 `LlmLongCat`，通过 LongCat API 开放平台接入云端大模型，替代/并存本地 Ollama。

### 关键信息（LongCat 文档）
- 接入端点：`https://api.longcat.chat/openai/v1/chat/completions`（OpenAI 兼容格式）
- 模型：`LongCat-2.0`（上下文 1M，输出最长 128K）
- 鉴权：`Authorization: Bearer <APP_KEY>`
- 支持 SSE 流式：`data: {"choices":[{"delta":{"content":"..."}}]}`，结束发 `data: [DONE]`
- 限流：HTTP 429，建议指数退避

### 架构改动
1. 新增 `Llm/ILlm.cs` 接口：`tts` / `RequestAsync` / `Interrupt` / `ClearHistory` / `Stop`。
   历史记录类型（OllamaSharp 的 Message vs 自定义 ChatMsg）不进接口，各实现自管。
2. `Llm.cs` 改为实现 `ILlm`（`public TtsMatchaIcefall tts` → `tts { get; set; }`）。
3. 新增 `Llm/LlmLongCat.cs`：HttpClient + 手写 SSE 解析（不引入 OpenAI SDK），
   逐句切分送 TTS 的逻辑与 Ollama 版一致。
4. `Asr.cs`、`Server.cs` 的 `llm` 字段类型 `Llm` → `ILlm`。
5. `Server` 构造函数按环境变量选后端：配了 `LONGCAT_KEY` 用 LongCat，否则回退 Ollama。

### 使用
```bash
set LONGCAT_KEY=你的key
cd server && dotnet run
```
未配 key 时自动回退本地 Ollama，其它功能不受影响。
